# OnePlus 8 Pro USB-C desktop mode research

Date: 2026-11-18. Public-source research only; no phone or proprietary service material was used.

## Finding

[V: OnePlus official specifications](https://www.oneplus.in/8-pro/specs?from=8pro) identify a USB Type-C port with USB 3.1 Gen 1, but do not advertise DisplayPort output. [V: Nura's public OnePlus 8 Pro release](https://github.com/darknagel/oneplus-instantnoodlep-nura-unofficial/releases) and its [DisplayPort test notes](https://github.com/darknagel/oneplus-instantnoodlep-nura-unofficial/blob/main/docs/displayport.md) report USB-C DP Alt Mode working on the exact IN2023/instantnoodlep handset: video, audio, monitor USB hub and charging together, tested up to 2880×1800 at 120 Hz, in both plug orientations. The implementation says all four SuperSpeed lanes are allocated to DP; USB 2.0 and charging remain available. This is strong hardware proof, although this repo has not run it.

## 1. Hardware and wiring

- [V: [OnePlus official specs](https://www.oneplus.in/8-pro/specs?from=8pro); [USB-IF USB 3.1 language guide](https://www.usb.org/sites/default/files/usb_3_1_language_product_and_packaging_guidelines_final_0.pdf)] The phone advertises USB 3.1 Gen 1, which is a 5 Gbit/s SuperSpeed link. The standard red Warp Type-C cable is documented as USB 2.0; use a suitable SuperSpeed cable for USB 3.x data. The 5 Gbit/s figure is the USB signaling rate, not DP video bandwidth.
- [V: OnePlusOSS public GPL kernel, [`kona-oem.dtsi`](https://github.com/OnePlusOSS/android_kernel_oneplus_sm8250/blob/cad09e061ef6/arch/arm64/boot/dts/vendor/qcom/kona-oem.dtsi#L1607-L1620), [FSA4480 board override](https://github.com/OnePlusOSS/android_kernel_oneplus_sm8250/blob/cad09e061ef6/arch/arm64/boot/dts/vendor/qcom/kona-oem.dtsi#L421-L423), [`kona-sde-display.dtsi`](https://github.com/OnePlusOSS/android_kernel_oneplus_sm8250/blob/cad09e061ef6/arch/arm64/boot/dts/vendor/qcom/kona-sde-display.dtsi#L280-L289), and [`kona-audio.dtsi`](https://github.com/OnePlusOSS/android_kernel_oneplus_sm8250/blob/cad09e061ef6/arch/arm64/boot/dts/vendor/qcom/kona-audio.dtsi#L172-L177)] The SM8250 USB controller uses the QMP USB3/DP combo PHY (`usb_qmp_dp_phy`). The public OnePlus display DT associates the downstream DP controller with the PM8150B PD PHY for attach detection and names FSA4480 as its DP AUX/SBU switch. The FSA4480-compatible node is on the QUP I²C bus; the board override sets its address to `0x42`. This is board-level evidence that the SBU/AUX path is switched toward the Type-C connector through an FSA4480-class part, not just an SoC capability claim.
- [V: [current public Nura mainline device patch 0060](https://github.com/darknagel/oneplus-instantnoodlep-nura-unofficial/blob/498f76983128/kernel-patches/0060-arm64-dts-qcom-sm8250-oneplus-instantnoodlep-wire-US.patch), [DP lane-rate patch 0138](https://github.com/darknagel/oneplus-instantnoodlep-nura-unofficial/blob/498f76983128/kernel-patches/0138-arm64-dts-qcom-instantnoodlep-allow-DisplayPort-link.patch), and [test notes](https://github.com/darknagel/oneplus-instantnoodlep-nura-unofficial/blob/498f76983128/docs/displayport.md)] The mainline board graph connects the Type-C SBU endpoint to FSA4480 and the SM8250 DP controller output to the USB3/DP QMP PHY. Its reported capture is four-lane DP up to HBR3, with DP AUX switched over SBU. The GPL downstream source has the corresponding legacy SDE DP/AUX switch description. The Nura mainline bring-up makes the route explicit as a modern DRM/Type-C graph.
- [V: [iFixit teardown](https://www.ifixit.com/Teardown/OnePlus+8+Pro+Teardown/133351)] The teardown documents the physical handset and port area, but is not a board schematic and does not prove the lane routing by itself. No public OnePlus service schematic showing the full connector-to-mux nets was found in this research. The more conclusive evidence is the OnePlus GPL DT plus the exact-device mainline report of working external video.
- [V: Nura [`docs/displayport.md`](https://github.com/darknagel/oneplus-instantnoodlep-nura-unofficial/blob/498f76983128/docs/displayport.md#L1-L19)] In four-lane DP mode the SuperSpeed pairs are DP, so SuperSpeed USB storage/networking is unavailable on that same link; USB 2.0 devices on the hub still work. [I] Two-lane DP could potentially retain USB 3.x, but this exact-phone report instead documents four DP lanes, so do not plan around simultaneous USB 3.x without separate testing.

## 2. Linux support and this port's Type-C work

- [V: mainline [RB5 device tree](https://kernel.googlesource.com/pub/scm/linux/kernel/git/stable/linux-stable.git/+/7603d8e78023e5883e075b4625fbdf059c6384f7/arch/arm64/boot/dts/qcom/qrb5165-rb5.dts#1494); [upstreamed RB5 enablement series](https://lore.kernel.org/linux-arm-msm/20230817145516.5924-1-dmitry.baryshkov@linaro.org/)] RB5 is the useful SM8250 mainline precedent. Its board DTS enables the PM8150B Type-C/PD PHY, declares the DisplayPort alternate mode, connects the Type-C mux/SBU route through its board redriver, enables `mdss_dp`, and links the DP controller to the QMP combo PHY. That series was accepted upstream. RB5 uses its own board redriver and topology; instantnoodlep uses its FSA4480 SBU/AUX switch.
- [V: mainline [SM8150-HDK commit](https://code.googlesource.com/linux/torvalds/linux/+/ba712fd55c7b635ad73c48b087a44e0e77d32abf)] The SM8150 HDK's upstream device tree also enables OTG, Power Delivery, DP Alt Mode and the DP controller. [V: [OnePlus 8T DP role-order report](https://lkml.iu.edu/hypermail/linux/kernel/2610.0/08715.html)] The OnePlus 8T (SM8250) has recent community DP bring-up activity; that report describes a Type-C alternate-mode registration race that made DP work only on some attach sequences. Treat it as relevant adjacent work and a warning to exercise role/attach ordering, not as evidence that the same fixes are needed on instantnoodlep.
- [V: [Linux Type-C alternate-mode API](https://www.kernel.org/doc/html/latest/driver-api/usb/typec_bus.html); [RB5 tree above]] For this PM8150B design, use the Type-C connector class, the Qualcomm PMIC Type-C/PD PHY driver, TCPM/DP alternate-mode handling, the FSA4480 mux, USB role switching, MSM DP controller, and QMP combo PHY. Qualcomm PMIC-GLINK/UCSI is a separate firmware-mediated Type-C architecture used on later Qualcomm platforms; it is not a prerequisite for this PM8150B/SM8250 board. Bindings and node graphs for the mux and PHY must match this board rather than be copied from RB5 verbatim.
- [V: Nura release and its [`kernel-patches/`](https://github.com/darknagel/oneplus-instantnoodlep-nura-unofficial/tree/498f76983128/kernel-patches)] This exact phone already has an independently maintained, patched mainline Linux DP path. Its report demonstrates the hardware and a working software route; it does not mean the current Omarchy Mobile kernel configuration has DP enabled or that its patches are already integrated here.
- [V: [`POWER-M5-PLAN.md` §3.3, R3](POWER-M5-PLAN.md); [`DAILY-K3-PLAN.md` §3](DAILY-K3-PLAN.md); [`kernel.config`](kernel.config)] Our M5 Type-C plan already specifies PM8150B Type-C/PD, `dr_mode = "otg"`, `usb-role-switch`, connector graph, and tests for role/orientation. The DAILY-K3 note says the live config resolves `CONFIG_TYPEC_QCOM_PMIC` to module (`=m`), despite the fragment comment asking for built-in, and that the current probe DT forces peripheral mode. [V: `POWER-M5-PLAN.md` §3.3 and `DAILY-K3-PLAN.md` status] The phone is currently used in USB gadget/peripheral mode for NCM networking. Host mode and DP mode have not been enabled in this project's current kernel.
- [I] The clean order is to finish the existing P3 Type-C gate first: demonstrate role switching without losing the known gadget fallback, then enumerate simple USB peripherals in host mode. Add DP connector/mux/DRM device-tree wiring and Kconfig only after that. DP testing must preserve an accessible recovery path and remain RAM-boot-only until the existing runbook authorizes further steps.

## 3. Fallbacks if direct DP is unavailable

| Path | What it needs | Feasibility |
| --- | --- | --- |
| DisplayLink USB graphics adapter/dock | [V: EVDI is a GPL virtual-display kernel driver, primarily used with DisplayLink's proprietary userspace](https://github.com/DisplayLink/evdi/blob/main/module/README.md#usage); [V: Synaptics distributes a separate DisplayLink Ubuntu driver](https://www.synaptics.com/products/displaylink-graphics/downloads/ubuntu). It still needs that compatible vendor userspace/USB protocol stack. | [I] Low-to-medium for a temporary demo, poor as a product path. ARM64 package support for this phone is not established by the official Linux download page; rendering/compressing frames and USB transfer add CPU, memory-bandwidth, latency, and battery cost. Prefer native DP when it is available. |
| USB graphics chip without DP Alt Mode | A USB framebuffer/display adapter that consumes ordinary USB data; simple USB-C-to-HDMI passive/DP adapters do not do this and still require Alt Mode. | [I] Low. Most practical USB graphics adapters are DisplayLink-class and inherit its driver, licensing, ARM64 and CPU constraints. A generic HDMI dongle is not a fallback if it expects DP Alt Mode input. |
| Miracast / Wi-Fi Display | [V: GNOME Network Displays](https://github.com/GNOME/gnome-network-displays) is an experimental Linux Wi-Fi Display sender and requires a screencast portal; its README lists GStreamer and network dependencies. | [I] Low-to-medium. Requires Wi-Fi Direct/P2P support in the phone's Wi-Fi stack, a compatible TV receiver, source encoding, and a working screencast path. It avoids the USB-C lane constraint, but adds latency and draws radio/encoder power. It is not an installed phone feature in the current bring-up. |
| Remote desktop to a receiver | Run an RDP/VNC/Sunshine-like server on the phone and use a TV/streaming box/computer as the client. | [I] Medium for a usable remote session; low for a standalone-TV experience unless the TV has a suitable client. It streams over Wi-Fi and is a useful fallback for desk or living-room use. Existing Omarchy Mobile `omamobile-mirror` is described as USB/VNC phone screen-and-input mirroring to a computer, the reverse direction from phone-to-TV [V: upstream [`omarchy-mobile` package map](https://github.com/derekross/omarchy-mobile)]. |
| PD passthrough while using a hub | Use a PD hub/dock that accepts charger input and negotiates source power to the phone while upstream data/DP is active. | [V: Nura reports simultaneous charging, video, audio and USB hub; its notes also say the phone can power a display/device or take power from a display that supplies it.] [I] On this repo's kernel, charging under our builds is not qualified [V: project state and `POWER-M5-PLAN.md`]; require the P3 role/PD tests and a separately reviewed charging policy before relying on it. |

## 4. Desktop userspace and convergence

- [V: [Hyprland monitor configuration](https://wiki.hypr.land/configuring/core/monitors/); [monitor events](https://wiki.hypr.land/configuring/core/advanced-configuration/events/)] Hyprland already supports multiple outputs, per-output mode/scale/position, mirroring, output hotplug events, and workspaces bound to monitors. Once DRM exposes a `DP-*` output, standard compositor configuration can place it at the preferred resolution and scale.
- [V: upstream [`omarchy-mobile` package map](https://github.com/derekross/omarchy-mobile), [`omamobile-shell` phone profile](https://github.com/derekross/omarchy-mobile/tree/main/packages/omamobile-shell), and its Omarchy patches] Omarchy's ordinary desktop environment and Hyprland workflow remain underneath the phone profile. The mobile package supplies a touch-first shell profile and mobile apps/adjustments; it is not a second compositor. Omarchy desktop components such as normal workspaces, tiling, launcher/bar/dock and desktop application set can therefore be used on an external monitor. [I] The external-display detection and profile transition need integration work; the currently documented phone profile is not an automatic convergence manager.
- [I] A useful convergence policy is: on a stable external DRM output plus a physical keyboard, put the external output at its preferred mode/scale, expose normal desktop window rules and dock/bar, and keep the handset display available as a touch control/secondary monitor; when the external output disconnects, restore the phone layout and touch-oriented window behavior. Keyboard presence alone should not trigger desktop mode. Keep manual override and persist per-user output layout. Hyprland output events can drive a small session service; the mobile shell can switch layout/config without replacing the compositor or restarting apps.
- [I] Desktop UI work is independent of initial USB host enumeration and can be prototyped against a virtual display or a second DRM output. The CPU/GPU cost is modest compared with video output itself, although the four-lane external DP allocation and the project's kernel stability remain gating concerns.

## 5. Feasibility and gated phone experiments

| Route | Verdict | Effort |
| --- | --- | --- |
| Native USB-C DP Alt Mode | [V] Physical path demonstrated by the exact-device mainline port. [I] Best route for a responsive, useful desktop; this project's current kernel still needs integration. | Medium-high: finish Type-C host/PD P3 first; port/review board-specific DP/FSA4480 graph and any needed kernel fixes; qualify panel/DPU and power interactions. A few focused engineering days to integrate known work, then phone qualification and bug fixing. |
| DisplayLink USB graphics | [I] Possible only if an arm64-capable userspace stack and acceptable performance are found. | High/uncertain; licensing and support risk, and performance/power poorer than native DP. |
| Miracast / remote streaming | [I] Useful fallback and less tied to Type-C muxing. | Medium for remote desktop, high for Miracast on this phone because P2P and the sender stack are unqualified. |
| Omarchy convergence UI | [I] The session/profile part is straightforward after an external DRM connector is stable. | Low-medium; requires hotplug/keyboard detection, monitor layout and touch/lock-screen regression testing. |

No experiments were performed for this report. Proposed owner-gated sequence, using the existing [`POWER-M5-PLAN.md` P3/R3 runbook](POWER-M5-PLAN.md):

1. [I] RAM-boot the approved Type-C P3 candidate and first test USB host mode with a low-power wired keyboard, then a mouse. Read back `/sys/class/typec/` roles and the USB role-switch state; verify gadget NCM returns after unplug/reboot and both plug orientations behave. Stop on a role stuck in source mode, unexplained VBUS/current draw, boot instability, or lost recovery access.
2. [I] Only after the host test passes, use a self-powered DP monitor/adapter and a USB-C cable known to support SuperSpeed. First validate display-only with the phone powered safely; then add keyboard/mouse through the monitor's USB2 hub, confirm DP and USB2 work together, and test dock PD passthrough last. Record mode, orientation, PD role/current, suspend/resume and unplug recovery. Stop on display-engine/USB crash, power/thermal anomaly, or inability to return to known-good gadget mode. Keep these as RAM-boot qualification steps; do not flash or change active slot as part of this research.
3. [I] After DRM hotplug is stable, test external monitor mode in Hyprland, then the desktop profile transition with and without a keyboard. Check lock-screen visibility, on-screen keyboard behavior, phone touch, scale, suspend/resume, and automatic restoration after disconnect.
