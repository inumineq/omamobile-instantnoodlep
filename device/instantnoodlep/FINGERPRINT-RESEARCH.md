# OnePlus 8 Pro fingerprint research

Date: 2026-11-18. Scope: public-source research only. No handset probing, proprietary binaries, or protocol extraction was performed.

## Findings

### Part, wiring, and secure ownership

- [V: OnePlusOSS `android_kernel_oneplus_sm8250`, `kona-oem.dtsi` at commit [`cad09e061ef6`](https://github.com/OnePlusOSS/android_kernel_oneplus_sm8250/blob/cad09e061ef6/arch/arm64/boot/dts/vendor/qcom/kona-oem.dtsi#L14-L34)] The public OnePlus GPL kernel describes `fingerprint_detect` (`compatible = "oneplus,fpdetect"`) and `goodix_fp` (`compatible = "goodix,fingerprint"`). The latter names TLMM GPIO 23 as IRQ, GPIO 68 as reset, and GPIO 125 as enable/power. The candidate LDO supply properties are commented out, and the node uses GPIO power mode; the active `pinctrl-0`/`pinctrl-1` groups confirm GPIO 125 high/low behavior. No sensor regulator is actively named in this node.
- [V: LineageOS continuation of the same public GPL device kernel, `kona-mtp.dtsi` at commit [`078365e5318d`](https://github.com/LineageOS/android_kernel_oneplus_sm8250/blob/078365e5318d/arch/arm64/boot/dts/vendor/oplus/instantnoodlep/kona-mtp.dtsi#L132-L170)] The IN2023-family board data identifies `goodix_optical_G6`, `chip-name = "G_OPTICAL_19811_G6"`, `vendor-chip = <11>` (Goodix), with a G5 alternative also listed. Its `goodix_fp` node repeats GPIO 23 IRQ, 68 reset, and 125 power; power is GPIO-switched (`power-mode = <2>`), with no regulator supply. This is the best public identification of the fitted family/revision. It does not prove every handset/display replacement has the same part; the DT contains both G5 and G6 mappings.
- [V: OnePlusOSS [`gf_spi.c`](https://github.com/OnePlusOSS/android_kernel_oneplus_sm8250/blob/cad09e061ef6/drivers/oneplus/input/fingerprint/goodix/gf_spi.c#L851-L918), [`gf_spi.h`](https://github.com/OnePlusOSS/android_kernel_oneplus_sm8250/blob/cad09e061ef6/drivers/oneplus/input/fingerprint/goodix/gf_spi.h#L121-L139), and [`Makefile`](https://github.com/OnePlusOSS/android_kernel_oneplus_sm8250/blob/cad09e061ef6/drivers/oneplus/input/fingerprint/goodix/Makefile)] Despite its filename, this build selects `USE_PLATFORM_BUS`, not `USE_SPI_BUS`. It creates a fingerprint misc/input device, configures IRQ and GPIO enable, and includes netlink support; there is no evidence in this public board integration of a Linux SPI child or Linux-visible image transfer path. The GPIO controls are AP TLMM lines, but source evidence points to a secure/vendor-mediated capture route rather than a normal Linux SPI driver.
- [V: [`goodix-fp-spi-linux`](https://github.com/wrobelda/goodix-fp-spi-linux), architecture section and [reference platform/test scope](https://github.com/wrobelda/goodix-fp-spi-linux#reference-platform)] The documented Goodix TEE architecture leaves image capture, template processing, and matching to a closed signed Trusted Application (TA) in Qualcomm QSEE; the normal-world kernel handles only power/reset/interrupt and does not access the SPI imaging stream. Its demonstrated platform is a Xiaomi Pad 5 Pro 5G with a capacitive GF3626, not this OnePlus phone. The project explicitly says portability to other part numbers and OEM TA profiles is unestablished and calls the in-display Goodix family untested. This is strong evidence for the expected architecture, but not a direct proof that OnePlus's exact G6 implementation uses the same TA ABI.
- [V: Nura OnePlus 8 Pro port status](https://github.com/darknagel/oneplus-instantnoodlep-nura-unofficial#status) records the fingerprint reader as “not done”; its image contains OnePlus proprietary sensor configuration but does not claim Linux fingerprint authentication. [I] Taken together, the likely OnePlus route is a Goodix G6 sensor with QSEE TA plus a proprietary vendor fingerprint HAL coordinating it. The public GPL DT and kernel driver do not expose a usable Linux image/matching path. Confirming the exact OnePlus TA/HAL boundary and TA name would require vendor Android artifacts or device investigation, neither performed here.

### Linux and mobile OS status

- [V: [`libfprint` supported devices](https://fprint.freedesktop.org/supported-devices.html)] Current libfprint's supported-device list names external USB sensors, including several FPC and Egis parts; it has no Goodix G6 UDFPS entry. [V: Nura status above] The OnePlus 8 Pro mainline port has not implemented its reader.
- [V: [`goodix-fp-spi-linux`](https://github.com/wrobelda/goodix-fp-spi-linux#status)] A recent independent Linux project reports a QSEE transport, sensor power/IRQ interfaces, a QSEE supplicant/TA loader, and a `libfprint` driver for one versioned Goodix TA profile, with fprintd/GDM tested on its reference Qualcomm SM8250 tablet. It also states its GW in-display sensor family is untested and that another OEM, sensor generation, or TA may have a different protocol. This is meaningful adjacent work, not confirmed instantnoodlep support.
- [V: `libfprint` project description](https://fprint.freedesktop.org/) describes libfprint as the device-communication/matching library and fprintd as the D-Bus daemon with PAM integration. [I] No public evidence found in the checked libfprint, mainline Linux, Nura/postmarketOS, or Sailfish/Ubuntu Touch device work establishes a working Goodix G6 in-display optical sensor on a Linux phone. A modern Goodix QSEE proof of concept on another SM8250 device does exist, so a blanket “no optical sensor can work on Linux” claim would be too broad; no demonstrated in-display optical UDFPS end-to-end Linux authentication was found.

### Requirements and effort

- [I] A complete path would need: (1) safe device-tree and kernel plumbing for GPIO/regulator/reset/IRQ and the secure QSEE interface; (2) the OnePlus-compatible signed Goodix TA and required listener-backed sealed storage, supplied lawfully from the owner's own factory image if licensing permits; (3) a compatible userspace QSEE supplicant/TA loader and TA protocol profile; (4) a `libfprint` driver and integration through fprintd, then PAM/lock-screen policy with rate limits and PIN fallback; and (5) display coordination that draws a bright white capture spot and switches the panel to its fingerprint high-brightness mode while capture is active. No proprietary TA or firmware belongs in this repository [V: `AGENTS.md`, rule 8]; no decompiled/proprietary implementation belongs here [V: `AGENTS.md`, rule 5].
- [V: Nura port reports OnePlus sensor configuration in its image](https://github.com/darknagel/oneplus-instantnoodlep-nura-unofficial#install); [V: QSEE Goodix project describes QSEE TA, listener services, and libfprint pieces](https://github.com/wrobelda/goodix-fp-spi-linux#what-is-where). [I] Reusing the existing AP GPIO and porting the panel illumination UI would be moderate effort. A legal and compatible TA path, OnePlus-specific QSEE ABI validation, and secure enrollment/authentication integration are high effort and may be blocked by signing/licensing. Overall: **high / uncertain feasibility**, likely several weeks of focused engineering even if the correct TA is usable; otherwise not feasible as a clean open-source upstream feature. Keep PIN/password unlock as the supported path until end-to-end evidence exists.

### UI placement and capture illumination

- [V: OnePlus 8 Pro public manual](https://service.oneplus.com/content/dam/support/user-manuals/common/OnePlus_8_Pro_User_Manual_EN.pdf); [V: public display specification](https://www.oneplus.com/pk/8-pro/specs?from=8pro) The manual labels an “In-Display Fingerprint Sensor” centered in the lower part of the display; public specifications give 1440 × 3168 pixels. The public GPL DT node does not encode display coordinates, and a checked LineageOS device resource search did not find an Android `physical_fingerprint_sensor_center_screen_location_*` override. [I] For an initial mockup only, use center x=720 and a lower-screen y around 0.76×3168 (about 2408 px), derived visually from the manual diagram; it is not a calibrated or source-exact coordinate. Do not make this value an enabled default until verified against a licensed OEM resource or on-device alignment.
- [I] Add an optional `udfps_center_px = x,y` and target radius to `device/instantnoodlep/device-ui.conf`, adjacent to `safe_insets_px`; keep coordinate units in native panel pixels and transform for rotation/scaling. A lock-screen layer-shell surface can paint the target above the lock surface and accept the placement cue without a fingerprint kernel driver. When authentication capture is requested, it can show the white spot and request the panel's HBM mode, then restore the prior state on completion/cancel/timeout. The UI must not claim authentication until a trusted backend reports success.
- [V: Nura `docs/patches.md` and `docs/panel-log.md`](https://github.com/darknagel/oneplus-instantnoodlep-nura-unofficial/tree/main/docs); [V: local panel implementation research, [`DISPLAY-M3-PLAN.md`](DISPLAY-M3-PLAN.md)] Panel and display control are separate from sensor capture. [I] Drawing/positioning the visual target is easy and independently reviewable; triggering the correct HBM sequence is moderate and depends on a supported panel control interface, which should be researched/implemented with the display subsystem plan before enabling it. A static target can still be prototyped independently.
